# AWE: Adaptive Agents for Dynamic Web Penetration Testing — 论文分析

## 论文信息
- **标题**: AWE: Adaptive Agents for Dynamic Web Penetration Testing
- **作者**: Akshat Singh Jaswal, Ashish Baghel（共同第一作者）
- **单位**: Stux Labs
- **发表会议/期刊**: Workshop on LLM Assisted Security and Trust Exploration (LAST-X) 2026, 2026年2月27日, San Diego, CA, USA（与NDSS Symposium联办）
- **论文编号**: ISBN 978-1-970672-05-3, DOI: 10.14722/last-x.2026.23037

## 一、核心产出

**贡献1: 提出AWE框架——一种记忆增强的多智能体自主Web渗透测试系统。**
AWE将结构化的、针对特定漏洞类型的分析流水线嵌入到轻量级LLM编排层中，不同于通用型智能体依赖大模型自由推理的方式。它在注入类漏洞上取得了显著的成绩提升，XSS成功率达87%（比MAPTA高30.5%），盲SQL注入成功率达66.7%（比MAPTA高33.3%），同时使用的模型（Claude Sonnet 4）远弱于MAPTA（GPT-5）。

**贡献2: 设计了三层架构——编排层、专用智能体层和基础服务层。**
编排层负责全局状态管理和资源治理；专用智能体层为每种漏洞类型（XSS、SQLi、SSTI、命令注入、XXE、SSRF、IDOR、LFI等）封装了领域专用的分析流水线；基础服务层提供持久化记忆系统、浏览器验证引擎、端点发现等共享基础设施。这种架构将领域知识嵌入系统设计而非仅依赖LLM推理能力。

**贡献3: 提出了结合上下文感知的负载变异与持久化记忆的确定性验证机制。**
AWE不依赖LLM生成随意负载，而是先通过结构化的探测推断服务器端的过滤策略、反射上下文和模板引擎类型，再将精确的上下文信息传递给LLM生成针对性负载。所有发现必须通过浏览器验证（XSS）或行为差异性验证（SQLi等），确保只有实际可利用的漏洞才被报告，从根本上消除了假阳性。

**贡献4: 在XBOW基准（104个挑战）上进行了全面的实验评估，揭示了架构专业化与通用推理能力之间的互补关系。**
AWE在注入类漏洞上显著优于MAPTA，但在需要长程推理的类别（权限提升、反序列化、业务逻辑）上不如MAPTA。论文证明了"架构设计与模型能力同样重要"的核心论断，并指明了混合架构的未来方向。

**贡献5: 实现了数量级的效率提升——token消耗降低98%，成本降低63%，求解速度快4.4倍。**
AWE总token消耗仅1.12M（vs MAPTA的54.87M），总API成本仅$7.73（vs MAPTA的$21.38），平均求解时间53.1秒（vs MAPTA的190.8秒）。这使得AWE适用于高频测试和持续集成流水线。

## 二、框架/架构设计

### 2.1 整体架构的三层结构

AWE采用三层架构设计，每一层有明确的职责边界：

**第一层：编排层（Orchestration Layer）**
- **职责**: 管理从初始侦察到多步利用的整个扫描进程；维护全局利用上下文（global exploitation context）；在所有组件之间进行协调和消息路由；强制执行资源治理（token消耗、运行时、工具成本的监控与调度）
- **核心组件**: Intelligent Orchestrator（智能编排器）
- **工作流程**: 编排器收集侦察结果 → 评估各漏洞类别的可行性 → LLM将侦察输出转换为优先级执行计划 → 选择满足前提条件的智能体子集执行 → 持续监控资源使用情况后决定早期退出还是继续

**第二层：专用智能体层（Specialized Agents Layer）**
- **职责**: 将领域知识编码为针对特定漏洞类型的自包含利用模块；将应用行为转化为漏洞特定的假设并通过结构化过程测试这些假设
- **包含的智能体**: XSS、SQL注入、盲SQL注入、服务器端模板注入（SSTI）、命令注入、XXE、SSRF、IDOR、LFI
- **核心特点**: 每个智能体实现为自包含的利用模块，采用结构化的操作流水线而非仅依赖LLM推理

**第三层：基础服务层（Foundation Layer）**
- **职责**: 提供所有智能体共享的基础设施服务
- **核心组件**: 持久化记忆系统（Persistent Memory System，分短期和长期记忆）、浏览器验证引擎（Browser Verification Engine）、端点发现/参数提取/技术指纹识别服务

### 2.2 各核心组件的详细设计

#### (A) Persistent Memory System（持久化记忆系统）

这是框架最关键的设计元素之一，分为两个子系统：

**短期记忆（Short-term Memory）**:
- 追踪尝试过的payload及其结果
- 记录推断出的过滤规则
- 记录智能体级别的进度标记
- 作用：防止在同一轮测试中重复尝试

**长期记忆（Long-term Memory）**:
- 记录领域级别的特征，如有效的绕过模式
- 特征性的sanitization特征
- 历史payload成功率
- 作用：将先前经验整合到未来的攻击中，类似于真实攻击者在反复与相似系统交互中积累知识

#### (B) Browser Verification Engine（浏览器验证引擎）

- **目的**: 对HTTP响应无法确认的漏洞类型提供最终的利用验证
- **工作方式**: 在受控的headless Chromium环境中执行payload
- **可观测信号**: 脚本执行（JavaScript execution）、DOM突变（DOM mutation）、对话框触发（dialog triggers）
- **意义**: 消除了整个类别的假阳性，区分理论可利用和实际可利用的漏洞

#### (C) 专用智能体详细工作流程——以XSS Agent为例

论文以XSS智能体为例展示了五阶段检测流水线：

**阶段一: 并行Canary注入（Parallel Canary Injections）**
- 发送多个标记性payload到目标端点
- 映射输入反射行为，分析是否存在反射型XSS的可能性

**阶段二: DOM上下文识别（Context Identification）**
- 区分细粒度的DOM上下文：
  - 带引号的属性（quoted attributes）vs 不带引号的属性（unquoted attributes）
  - JavaScript字符串字面量（JavaScript string literals）
  - 原始HTML插入（raw HTML insertion）
- 之所以区分这些是因为后续payload的可行性完全取决于上下文正确性

**阶段三: 服务器端过滤推断（Filter Inference）**
- 执行目标探测以推断服务器端过滤策略
- 包括字符级变换、被阻止的标签族、事件处理器限制等
- 将这些信息打包为结构化格式传递给LLM

**阶段四: LLM负载合成（LLM Payload Synthesis）**
- LLM根据发现的具体约束条件合成候选payload
- 此设计避免了LLM驱动系统中常见的推测性或幻觉漏洞
- 将LLM的创造力扎根于精确的上下文信息中

**阶段五: 浏览器验证（Browser Verification）**
- 要求JavaScript执行的明确证据
- 通过headless Chromium执行payload并观察实际行为

**其他智能体设计**:

- **SQLi Agent**: 结合确定性payload集合与从数据库错误消息、后端指纹识别和观察到的查询结构模式推断出的上下文；应用受控变异以探索替代执行路径或WAF绕过
- **SSTI Agent**: 部署引擎特定的探针以区分流行的模板框架（如Jinja2、Twig、Freemarker等），根据检测到的引擎内部语义构建利用字符串
- **IDOR Agent**: 依赖认证后的差异性测试（authenticated differential testing），比较跨资源标识符的访问模式以检测授权不一致

### 2.3 组件间交互与数据流

1. **侦察阶段**: Foundation Layer的端点发现和参数提取服务扫描目标应用 → 输出攻击面信息给编排层
2. **优先级排序**: 编排器将侦察结果传递给LLM → LLM输出优先级执行计划 → 编排器选择合适的专用智能体
3. **漏洞分析阶段**: 专用智能体执行各自的流水线 → 使用Foundation Layer的持久化记忆记录进度 → 使用浏览器验证引擎确认发现
4. **结果聚合**: 验证后的结果返回编排器 → 编排器决定是否继续其他智能体或提前退出

### 2.4 关键设计决策与动机

**决策1: 专业化优先于通用推理（Specialization over Generalized Reasoning）**
- 动机: 细粒度利用需要领域特定的程序，这些程序更适合作为专用状态机和推理流水线实现，而非依赖LLM的通用推理。论文认为LLM在结构化任务上的表现不如专用管道可靠。

**决策2: 有状态与记忆驱动操作（Stateful and Memory-driven Operation）**
- 动机: 现代利用依赖于跨越多轮请求、输入转换和上下文线索的多步推理；无状态扫描器或无约束的LLM智能体无法可靠维护这样的上下文。

**决策3: 验证优先于推测（Verification rather than Speculation）**
- 动机: 每个发现必须有具体证据支持——可观察的执行、差异性行为或成功的数据提取——确保系统只报告真实攻击者可以利用的漏洞。

**决策4: LLM作为咨询机制而非生成引擎**
- 编排器中，LLM的功能是解释上下文线索（如反射参数、sanitization行为、语言特定模板结构）并提出建议，而非直接生成payload。这避免了在不同上下文中产生不相关或幻觉payload的效率问题。

**决策5: 资源治理与早期退出策略**
- 监控token消耗、运行时和工具成本；可以在高影响力发现后早期退出，或在低收益智能体上缩减投入。

### 2.5 技术栈与协议

- **交互协议**: 标准的HTTP（GET和POST请求），参数放置（parameter placement）用于探索多输入通道
- **浏览器引擎**: headless Chromium用于XSS验证
- **LLM API**: 商业LLM API，最终选用Claude Sonnet 4
- **目标应用栈**: PHP、Python、Node.js、Java等常见框架
- **隔离环境**: 每个挑战在隔离容器中运行，防止交叉污染

## 三、实验/评估设计

### 3.1 基准（Benchmark）

**XBOW基准（主要评估）**:
- 规模: 104个容器化的脆弱Web应用挑战
- 覆盖范围: 26种漏洞类别
- 多样性: 从简单的单步注入到多步骤利用链（涉及认证、授权、上下文特定的sanitization绕过）
- 注入类漏洞占多数，反映了真实世界的漏洞分布
- 每个挑战嵌入了隐藏flag，必须通过完整的端到端利用才能获取
- 来源: XBOW Engineering的开源验证基准（https://github.com/xbow-engineering/validation-benchmarks）

**DVWA（模型选择实验）**:
- Damn Vulnerable Web Application，提供可重复的脆弱性配置和可配置的安全级别
- 仅用于模型选择阶段的受控实验
- 聚焦于5种漏洞类型：反射型XSS、存储型XSS、DOM型XSS、基于错误的SQL注入、基于时间的盲SQL注入
- 每轮每个漏洞类型执行n=10次独立试验以获得可靠的估计
- 提供低、中、高三个安全难度级别

### 3.2 基线方法（Baselines）

**MAPTA（Multi-Agent Penetration Testing AI）**:
- 选择原因: 最强的公开可用自主渗透测试框架
- 架构: 三角色多智能体架构——Coordinator（高层规划）、Sandbox（在隔离Docker环境中执行命令和脚本）、Validation（将候选利用转化为已验证的PoC）
- 使用的模型: GPT-5（扩展推理模式），远强于AWE的Claude Sonnet 4
- 在XBOW上已报告的解决率: 76.9%

### 3.3 评估指标

- **有效性**: 总体解决率、按类别解决率、唯一解决挑战数
- **效率**: 求解时间（Time-to-solve）、每个成功利用的token使用量
- **成本**: 总API支出、每个解决挑战的摊销成本
- **成功标准**: 严格标准——挑战被视为解决仅当通过验证的利用获取了正确的flag。部分进展不计入有效性指标。

### 3.4 实验配置

- **AWE配置**: 激进配置（aggressive configuration）——执行深度侦察和编排器认为相关的所有智能体
- **时间预算**: 每个挑战10分钟（与MAPTA配置一致以确保可比性）
- **硬件**: 所有实验在相同硬件上执行
- **隔离**: 每个挑战在隔离环境中运行，防止交叉污染
- **记忆重置**: 挑战之间重置记忆状态以评估单轮表现
- **浏览器验证**: 使用一致的headless Chromium配置
- **模型选用**: Claude Sonnet 4用于所有主要实验（基于DVWA预实验的选择）

## 四、实验结果

### 4.1 DVWA实验结果（模型选择阶段）

| 漏洞类型 | Claude Sonnet 4 | GPT-4o | Gemini 2.0 Flash |
|---------|----------------|--------|------------------|
| 反射型XSS | 100% | 100% | 100% |
| 存储型XSS（CSP生效） | 67% | 67% | 50% |
| DOM型XSS | 80% | — | — |
| 基于错误的SQL注入 | 80% | — | — |
| 盲SQL注入 | 70% | 60% | 55% |

**迭代效率**:
- Claude Sonnet 4: 收敛于10-40次payload尝试
- GPT-4o: 需要多约20%的尝试次数
- Gemini 2.0 Flash: 需要多约40%的尝试次数
- 难度级别越高，所需payload尝试次数越多（低难度平均10次，中难度20次，高难度40次）

### 4.2 XBOW基准总体结果

| 系统 | 解决率 | 平均时间(秒) | 模型 |
|-----|-------|-------------|------|
| AWE | 51.9% (54/104) | 53.1 | Claude Sonnet 4 |
| MAPTA | 76.9% (80/104) | 190.8 | GPT-5 |

**效率与成本对比**:

| 指标 | AWE | MAPTA | 改进幅度 |
|-----|-----|-------|---------|
| 总token消耗 | 1.12M | 54.87M | 减少98% |
| 每解决挑战token | 20.7K | 685.9K | 减少97% |
| 总API成本 | $7.73 | $21.38 | 减少63% |
| 每解决挑战成本 | $0.113 | $0.267 | 减少58% |
| 平均求解时间 | 53.1秒 | 190.8秒 | 快4.4倍 |
| 中位求解时间 | 35.7秒 | 156.2秒 | 快4.4倍 |

### 4.3 按类别实验结果

| 漏洞类型 | 总数 | MAPTA解决数(%) | AWE解决数(%) |
|---------|------|---------------|-------------|
| XSS | 23 | 13 (57%) | **20 (87%)** |
| 盲SQLi | 3 | 1 (33%) | **2 (67%)** |
| SQLi | 6 | 6 (100%) | 6 (100%) |
| XXE | 3 | 3 (100%) | 3 (100%) |
| SSRF | 3 | 3 (100%) | 3 (100%) |
| SSTI | 13 | **11 (85%)** | 7 (54%) |
| 命令注入 | 11 | **9 (82%)** | 5 (45%) |

**关键发现**:
- AWE在XSS上大幅领先（+30.5%），尤其擅长需要精确payload结构对齐反射上下文的场景
- 在经典注入家族（SQLi、XXE、SSRF）上两者表现相当
- MAPTA在SSTI（85% vs 54%）和命令注入（82% vs 45%）上显著领先
- AWE在盲SQL注入上胜出（+33.3%），归因于结构化的推断工作流和后端特定的时序探针

### 4.4 失败案例分析

**AWE失败的50个挑战**:
- 约1/3（约17个）对应AWE故意排除在范围外的漏洞类别（业务逻辑、反序列化、密码学误用）
- 约1/4（约12个）需要多步推理和有状态利用链——AWE的智能体目前无法表达
- 其余来自：认证异常、重型过滤抵抗了AWE的变异引擎、极窄的利用窗口（如竞态条件）

**两者的失败重叠**:
- 15个挑战两个系统都失败，反映了这些挑战的极端难度

**AWE独家解决的挑战**:
- 主要分布在XSS和盲SQL注入类别
- 这些案例通常需要精确的payload与反射上下文对齐、基于观察响应的自适应过滤绕过、以及多编码变换推理

**MAPTA独家解决的挑战**:
- 集中在需要探索、多智能体状态管理和语义推理的类别

### 4.5 定性分析

**行为模式**:
- AWE采用"先理解后利用"的策略——先通过结构化探测理解服务器行为，再针对性生成payload
- MAPTA采用"广泛探索"策略——利用GPT-5的强大推理能力和沙箱执行广泛尝试

## 五、讨论与局限

### 5.1 关键Insight

**架构与模型能力同等重要**: 论文最核心的发现是——利用成功率至少同样依赖于架构先验知识（architectural priors）和原始模型能力（raw model capability）。AWE使用更弱的模型但在特定类别上超越MAPTA，说明了这一点。

**专业化与通用推理的互补性**: 两个系统的对比揭示了明确的取舍——精确利用受益于结构化，而广泛覆盖受益于灵活性。最有效的自主渗透测试系统可能是将结构化漏洞分析与通用探索推理相结合的混合架构。

### 5.2 局限性

- **范围限制**: AWE仅针对注入型漏洞，不涉及业务逻辑漏洞、复杂认证工作流或协议级问题
- **有限的多步规划能力**: 智能体在基本独立的流水线中运行，不协调多阶段利用序列
- **对启发式抽象的依赖**: AWE的上下文和过滤器模型编码了对服务器行为和sanitization模式的假设，高度特化的框架可能使这些抽象失效
- **LLM敏感度**: 模型依赖的推理变异性仍是系统性约束，模型行为或定价的变化可能影响长期稳定性

### 5.3 领域启示

- 多智能体系统在安全测试中展现巨大潜力，但架构设计比模型选择更为关键
- 开源框架将促进该领域的研究
- 混合架构可能是未来的发展方向——将专用智能体的精确性与通用智能体的灵活性结合

## 六、总结

本文提出了AWE，一个记忆增强的多智能体自主Web渗透测试框架，其核心创新在于将领域特定的漏洞利用知识嵌入系统架构而非仅依赖LLM的通用推理能力。AWE采用三层架构——编排层负责全局协调与资源治理，专用智能体层为每种注入类漏洞封装结构化分析流水线，基础服务层提供持久化记忆和浏览器验证等共享基础设施。在104个挑战的XBOW基准上，AWE在XSS上达到87%的成功率（比MAPTA高30.5%），盲SQL注入达到66.7%（比MAPTA高33.3%），同时实现了98%的token消耗降低、63%的成本节省和4.4倍的加速，尽管使用的模型（Claude Sonnet 4）远弱于MAPTA的GPT-5。论文有力证明了"架构设计与模型推理能力同等重要"的核心论断，揭示了专业化智能体与通用推理智能体在渗透测试中的互补关系，为未来混合架构的自主安全测试系统指明了方向。
